The Five Names of One Electrode

A single recording site gets renamed four times between the silicon and Kilosort's (x, y). Mapping is nothing more than keeping those names in sync. Start with H3, where the chain is a straight line — then H10, where it isn't.

Built from the code and figures in Kilosort/ · H3 · H10-D (ASSY-77)

01

The problem is naming, not geometry

Kilosort never sees your probe. It sees a flat binary of 64 columns and a text file that says where each column sits in space. Everything that could go wrong lives in the gap between those two — and that gap is made of renames.

The same physical electrode carries five different identities on its way through the pipeline. Each handoff is a chance for the order to shift:

1 · SILICONsiteNth site down the shank. Physical. Has no number yet.
2 · PROBEpin 21Connector pin, fixed at manufacture. Vendor's numbering.
3 · AMPLIFIERhw 84Raw ADC channel on the DigitalLynx SX.
4 · CHEETAHCSC1Logical name. This is where the unscramble happens.
5 · KILOSORTch 00-based binary column, plus an (x, y) from the .prb.

The whole job: make sure that when Kilosort reads column i of the binary and looks up geometry[i], it gets the position of the electrode those samples actually came from. Nothing in the pipeline checks this for you.

02

The seven stages, once

Both probes travel the same seven stages. Only two of them do anything interesting; the other five are passthrough. Learn the chain here and the H3 / H10 difference collapses into one question — what does stage C actually say?

  1. A

    Physical electrode sites

    Silicon. Sites exist in a fixed spatial order, top of shank to tip. No numbers yet — numbering is a convention applied later.

  2. B

    Headstage / EIB wiring

    Copper traces on the adapter board, set when it was manufactured. Not a file, not configurable, not inspectable from software. Site → raw ADC channel.

  3. C

    Cheetah .cfg — -SetChannelNumber

    The only unscramble step in the entire pipeline. One line per channel: -SetChannelNumber "CSC1" 84 means "what everything downstream calls channel 1 is really raw hardware pin 84." Get this right and everything after it can stay simple.

  4. D

    Neuralynx writes CSCn.ncs

    The logical number from stage C becomes the literal filename. From here on, "CSC1" is a name every downstream tool inherits and trusts without re-deriving.

  5. E

    perpl_NLX2Binary.m

    Loops for CSC = 1:64 and writes each channel's samples in that exact numeric order. No geometry, no reordering — pure passthrough. Kilosort channel index = CSC number − 1.

  6. F

    kilosort_automation.py handoff

    Kilosort receives exactly two things about your recording: CSC_Raw.dat and probe_config.prb. It never sees stages A–E. It trusts the .prb completely.

  7. G

    probe_config.prb geometry

    The second place with real content. A dict of {channel index: (x, y)} in µm. Whitening, template matching, drift correction and unit depth all fall out of these numbers alone.

So: C and G are the only two stages that carry information. A, B are physics; D, E, F are bookkeeping. If C's table and G's geometry describe the same probe in the same order, the pipeline is correct. If they don't, nothing downstream will complain — you'll just get spikes assigned to the wrong depths.

03

H3 — one shank, one column, one straight line

H3 is the case worth learning first, because the answer turns out to be the simplest thing you could have hoped for: CSC number is depth rank. CSC1 is the shallowest site, CSC64 is the tip, and every step between them is one 20 µm hop down the shank.

That is not obvious from the config, though. Stage C for H3 is a genuine scramble — the hardware channels arrive in an order that looks random.

Trace one channel, end to end

1

Why the straight line is allowed here

Two independent facts make H3's simple y = i × 20 geometry correct rather than merely convenient:

1. The table is a hardware constant, not a per-session setting. The -SetChannelNumber block is byte-identical across every H3 config on file from 2023 through 2026 — a one-time calibration for this headstage, verified by direct comparison, not an assumption.

2. Insertion order confirms the direction in vivo. During probe descent, signal appears on CSC64 first, then 63, 62 … down to CSC1 last. CSC64 is the tip; CSC1 is the top. So consecutive CSC numbers really are consecutive physical sites — and since the .prb puts channel 0 at y = 0 and channel 63 at y = 1260, "larger y = deeper" is correctly oriented. The geometry is not mirrored.

# probe_config.prb — the entire H3 geometry
channel_groups = {
    0.0: {
        'channels': [0, 1, 2, ..., 63],
        'geometry': {
            0:  (5.5,    0.0),   # CSC1  — shallowest, enters tissue last
            1:  (5.5,   20.0),
            2:  (5.5,   40.0),
            ...
            63: (5.5, 1260.0),   # CSC64 — tip, enters first, deepest
        },
        'graph': [],           # empty on purpose — see below
    }
}

x = 5.5 is a constant — a nominal shank half-width, meaningless on a single-column probe. graph is deliberately empty: Kilosort derives spatial neighbours straight from the geometry, which is exactly why stage C being right matters so much. Whitening, templates, drift and unit depth all fall out of those (x, y) pairs and nothing else.

One caveat that trips people up. A probeinterface sanity check will report that this .prb has "the same geometry, different channel order" from every library ASSY-*-H3 entry. That is not a bug in your data. The library encodes Cambridge NeuroTech's Omnetics pin order for Intan-based acquisition (OpenEphys / SpikeGLX). Your chain is Neuralynx DigitalLynx SX + Cheetah, and its unscramble already happened at stage C, before the .ncs files existed. The comparison was against the wrong reference convention.

04

H10-D — two shanks, and a straight line can't describe it

Everything structural changes at once. H10-D has two shanks — the connector calls them Back and Front — with 32 sites each, arranged in 22 depth rows that alternate between single centre contacts and left/right pairs, tapering to singles near the tip. Row pitch is 15 µm; the two columns sit ±18.5 µm off centre; the shanks are 150 µm apart.

No single line of y = i × pitch can represent that. Two sites can share a depth. Two sites at the same depth can be on different shanks, 150 µm apart, and must never be treated as neighbours. H10 needs its own probe file.

The decode: subtract 63

The surprise is how clean stage B turns out to be for this probe. Take any raw hardware channel from this session's config and subtract a constant:

# the entire H10-D decoding rule
probe_pin = raw_hw_channel - 63

# CSC1–32  → "Back"  shank, top → tip, in order
# CSC33–64 → "Front" shank, top → tip, in order

That recovers the vendor pinout exactly for 63 of 64 channels. The headstage isn't scrambling anything at the board level — it's simply plugged into a hardware port that starts at ADC channel 64. The apparent chaos you see plotting CSC index against hardware channel comes entirely from CSC numbers being assigned in physical depth order per shank, not in pin order.

Selected site

The one channel that doesn't decode

CSC32 maps to raw hardware channel 60. 60 − 63 = −3, which is not a probe pin. It is the only channel in the table that fails, and every other channel claims a distinct real site — leaving exactly one physical position unclaimed: pin 48, the tip of the Back shank.

That leaves two live hypotheses, and the data can settle it:

  • (a) It really is the Back tip, routed some other way. Its trace should look like a normal tip-depth signal, continuous with its neighbours.
  • (b) It's a REF/GND tap. The vendor PDF documents several connector pins as dedicated reference or ground rather than recording sites. Then the trace should look flat and reference-like — and it has no spatial position at all.

The generated probe_config_H10D.prb parks channel 31 at pin 48 as a geometric placeholder and says so in its own header. Until it's resolved, the honest thing is to exclude it:

run_kilosort(settings=settings_main,
             probe_name='probe_config_H10D.prb',
             filename=f'{data_path}\\CSC_Raw.dat',
             bad_channels=[31],   # CSC32 — unresolved, see .prb header
             ...)

Worth noticing: the H3 table also contains a 60 — at CSC59. Same hardware channel, different probe. Whatever port or tap 60 corresponds to, it shows up in both chains, which is mild circumstantial support for hypothesis (b).

How far does the −63 rule actually reach?

Not as far as you'd like. Parsing every H10 config in Config files/ turns up three distinct -SetChannelNumber tables. Subtracting 63 produces valid-looking pin numbers for all of them — but only one puts CSC1–32 on the Back shank and CSC33–64 on the Front:

This is the sharpest trap on the page. "Subtract 63" is not a property of the H10 probe — it's a property of which hardware port that headstage happened to be plugged into, for those two files. Tables 1 and 2 still decode to real pin numbers, so an arithmetic check alone would pass them; it's the shank assignment that comes out wrong. probe_config_H10D.prb is valid for table 3 and nothing else.

05

Four ways this breaks silently

None of these throw an error. Kilosort runs, produces clusters, and reports depths. The output is simply wrong in a way that looks entirely plausible.

Reusing one .prb across probes

kilosort_automation.py defaults probe_name='probe_config.prb' for every call. That file is the 64-channel single-shank H3 line. Point an H10 session at it and both shanks get collapsed onto one imaginary column — sites 150 µm apart become "neighbours" for whitening and template matching.

GuardPass probe_name explicitly, per probe type. Never let it default.

Reusing one .prb across H10 sessions

Unlike H3's frozen table, the H10 configs on file carry three distinct -SetChannelNumber tables, and only one of them puts CSC1–32 on the Back shank. A .prb generated from one session's config is valid only for sessions sharing that exact table — and the arithmetic check won't catch it, because the wrong tables still decode to real pin numbers.

GuardDiff the session's -SetChannelNumber block against the one the .prb was built from. Not equal → regenerate, and name the source config in the header.

Off-by-one at the binary boundary

The .ncs files are named 1–64. Kilosort indexes 0–63. Stage E's loop is what ties them: channel index = CSC number − 1. The same shift applies to bad_channels — excluding CSC32 means passing 31.

GuardState the convention in the .prb header and check one known-bad channel end to end before trusting a batch.

Checking against the wrong reference

Comparing your .prb to probeinterface's vendor library flags a mismatch on every H3 variant. The library describes an Intan/Omnetics chain, not a Neuralynx one. A "failed" check against an irrelevant convention is worse than no check — it burns trust in a file that was fine.

GuardVerify against ground truth from your chain: the session .cfg, the vendor pinout PDF, and in vivo insertion order.

06

Check yourself

CSC17 on H3 maps to hardware channel 64. Does that mean it's the first site on the probe?

No. Hardware channel numbers carry no spatial meaning at all — they're just which amplifier input the trace happens to land on. CSC17 is the 17th site down the shank, at y = 320 µm, regardless of what stage B's wiring did. Its neighbours are CSC16 and CSC18, not "hardware 63 and 65."

On H10-D, are CSC32 and CSC33 physically adjacent?

No — they're about as far apart as two sites on this probe can be. CSC32 is the last channel on the Back shank (nominally the tip), and CSC33 is the first channel on the Front shank (the top, y = 0). Numeric adjacency in CSC space says nothing about spatial adjacency once there's more than one shank. This is exactly the assumption a single-shank .prb quietly encodes and gets wrong.

Kilosort ran without errors on an H10 session using the H3 probe file. Is the output usable?

No. Kilosort has no way to detect the mismatch — it received 64 columns and 64 positions, which is internally consistent. But it built its neighbourhood structure from a 1260 µm single line that doesn't exist, so whitening pooled channels that aren't neighbours, templates spanned imaginary distances, and every reported unit depth is fiction. Re-run it with a probe file generated from that session's config.

Why does the H3 .prb set every x to 5.5 — where does that number come from?

Nowhere meaningful. It's a nominal shank half-width placeholder. On a single-column probe every site shares one x, so the value is arbitrary as long as it's constant — only the differences between positions affect Kilosort's spatial reasoning. On H10 that stops being true: x becomes load-bearing, encoding both the ±18.5 µm column offset and the 150 µm shank separation.

You get a new H10 recording from a config you haven't seen. What's the minimum you check before sorting?

Parse that config's -SetChannelNumber block and diff it against the table your existing .prb was built from. Equal → reuse the file. Not equal → do not just re-run the arithmetic and call it verified: two of the three H10 tables on file decode to perfectly valid pin numbers while still scattering CSC1–32 across both shanks. The check that matters is the shank one — confirm CSC1–32 land on Back top-to-tip and CSC33–64 on Front top-to-tip. If they don't, the −63 rule doesn't apply to that session and the mapping has to be worked out from the pinout PDF again.
